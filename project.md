A self-hosted pipeline that turns a tap on an iPad into the right movie, at the right quality, sitting in qBittorrent — with every torrenting decision made and hidden in the backend. The family browses TMDB-style, taps "Add to Plex," and never sees a torrent name.

## Target environment

- **Host:** TrueNAS SCALE, deployed as a Custom App (Docker Compose–based). Custom App YAML supports both `image:` (pull) and `build:`/`dockerfile_inline` (build on the NAS from source).
- **Torrent client:** qBittorrent (v4.x/v5.x), WebUI enabled, already running as its own existing TrueNAS app — not deployed by this project.
- **Search mechanism:** qBittorrent's internal Search Plugins, driven asynchronously via `/api/v2/search/start`, `/status`, `/results`, `/delete`, using the `qbittorrent-api` Python library's `search.start()` job object.
- **Metadata/browse source:** TMDB API — search, discover-by-watch-provider, popular/trending, alternate titles.
- **Client device:** iPad, Safari, touch-first, "Add to Home Screen" standalone mode.
- **Repo:** git repo already initialized at this project root, remote `origin/main` configured.

## Confirmed architecture (not open for re-litigation)

- **Three logical components, one deployable app:**
  1. **Frontend container** — a single static HTML file (no framework, no build step) served by nginx, which reverse-proxies `/api/*` to the backend. Only component with a published port.
  2. **Backend container** — FastAPI automation engine. No published port; reachable only from the frontend container over the internal Compose network (`backend:8000`).
  3. **qBittorrent** — existing separate app, reached by the backend over the network.
- **Same-origin only.** All client traffic goes through the frontend's single exposed port — no CORS, no two-port setup.
- **Filter on structured API fields**, not filename regex, wherever possible (`fileSize`, `nbSeeders`). Only resolution, language, source, codec and container need filename token parsing — always whole-token, normalized matching, never substring.
- **Deploy is git-pull-based, not live-reload-on-edit.** A working copy (wherever edits happen) is fully decoupled from a deployed copy bind-mounted into each container. The deployed copy only changes via `git pull`. Backend picks it up via `uvicorn --reload`; frontend picks it up on next request since there's no build step. Rollback is `git checkout`/`git revert` on the deployed copy.
- **Self-update endpoint** (`POST /api/admin/deploy`) runs exactly `git pull`, hardcoded, no path/branch/command ever accepted as input. Gated by a plain, visible "Check for updates" button inside the Settings panel — not real auth, an accepted risk (see Stage 6; originally planned as a hidden long-press, changed to a visible button mid-Stage-6 per explicit user direction, prioritizing simplicity over obscurity — the accepted-risk reasoning is unchanged either way).
- **Explicitly out of bounds:** mounting the Docker socket into the backend. Self-update means "pull my own repo," nothing more privileged.
- **Requests are serialized** through a single `asyncio.Lock` — no distributed job queue, sufficient at household scale.
- **Job/request state persists in SQLite** on a volume, surviving container restarts.
- **No family profiles in the UI.** One shared Settings panel instead of per-user identity; the audit trail tracks what was picked, not who asked.

## Design principles carried through every stage

- **Pipeline as a library.** Search → filter → score → select → add is plain Python with no FastAPI dependency. The API is a thin wrapper, which is what makes it CLI-testable before any web layer exists.
- **One normalizer, many uses.** The same token-normalization utility matches resolution, language, source, codec, container, and title/year relevance — not several ad hoc string checks.
- **Two passes, never one.** "Is this actually the right movie" (relevance) and "which release of it is best" (quality) are different problems, solved differently — the first stays conservative and rule-based, the second is where the rich scoring lives.
- **Fail safe, not best guess.** When a match is ambiguous, the system reports "no qualifying results" rather than confidently downloading something close-but-wrong.
- **Hidden, never unrecoverable.** The family never sees torrent names or seeder counts — but every job keeps the candidate it picked, the search variant that found it, and its score breakdown, so a wrong download can be audited after the fact.
- **Secrets never reach the browser.** TMDB key, Plex token, git deploy key — all server-side only. The frontend hotlinks TMDB's public image CDN directly; every data call goes through the backend proxy.
- **Deploy is one fixed verb.** `git pull`, hardcoded. No Docker socket, ever.
- **Same origin, one door.** nginx is the only published port.

### Stage 2 — Match, score & add pipeline
*Depends on: Stage 1, Stage 0. The core engine.*

**Purpose:** Two passes. **Pass one** (relevance gate): is this candidate actually the title Stage 1 resolved? Conservative, rule-based. **Pass two** (quality score): among everything that survives pass one, which release is best — ranked by source, codec, container and size, not just seeders?

**Deliverables / done when:**
- Search executor: `search.start()` per variant, polled via `.status()` against a 45–60s ceiling, results via `.results()`, `.delete()` always in `try/finally`.
- **Pass one:** normalized-title overlap against every Stage 1 title variant, plus year within ±1, plus a resolution *floor* (see below), language allow/blacklist, and a cam/telesync/screener blocklist (`cam`, `hdcam`, `ts`, `telesync`, `screener`, `r5`, etc. — always on, unlike the language lists which default open) — all via the shared token utility, no fuzzy-distance matching. The cam blocklist only catches an *explicitly*-tagged bootleg; a real-world test on a movie 5-6 weeks past theatrical (Spider-Man: Brand New Day, 2026) found the only real risk case was releases with no source tag at all (`4K (Small File)`), which this can't catch since there's nothing to match against — noted as a known gap, not solved here.
- **Pass two:** weighted composite score, resolution (2160p/4K > 1080p > 720p > 480p) ranked above source type (REMUX > BluRay/BDRip > WEB-DL > WEBRip > HDTV), codec (HEVC/x265 > AVC/x264), seeder health (a coarse tier — e.g. 100+/30+/10+ — not raw count), and container (MKV > MP4 > other) — same token utility. Seeder health outranks container, not the reverse: container is a weak, easily-missing signal (a REMUX's container is very often left unstated since MKV is the de facto default) while a large swarm-size gap is a real practical difference — a live cross-check confirmed a well-seeded release with no stated container losing to a barely-seeded one that merely spelled its container out. `nbSeeders` is a real (if bounded) term in the composite, plus a practical viability floor before scoring even starts and a final known-then-raw-count tiebreaker (ahead of size) after — never able to override resolution, source, or codec, since Stage 0 found ~50% of real rows report it as unknown. File size (already bounded by a configured GB range) breaks any remaining near-ties.
  - *Worked example (from your Dune case):* of `dune.2160p.remux.webdl.mkv` (40GB), `dune.2160p.HEVC.remux.mkv` (85GB), and `dune.2160p.h264.webdl.mp4` (34GB), the second wins — best source (remux) + best codec (HEVC) + best container (mkv), with size confirming it. (All three sit at the same resolution tier, so resolution doesn't move this particular example — it only starts to matter once candidates at different resolutions are being compared, which is exactly the fallback case below.)
- **Resolution as a floor, not a fixed gate:** a `MIN_RESOLUTION` setting (default `2160p`, editable in Stage 7) — any candidate at or above that tier passes pass one; resolution is then the highest-weighted tier in pass two, so a 2160p release always outranks a 1080p one when both qualify, but a 1080p release is still accepted once the floor is lowered and nothing higher is available. This is what makes "prefer 4K, fall back to 1080p if nothing at 4K qualifies" work inside a single search pass, with no separate resolution-specific retry loop. A candidate with no recognized resolution token at all still fails the floor regardless of setting — fail-safe, not a guess.
- Fallback loop across Stage 1's variants, stopping at the first that produces any gate-passing candidate.
- Dedup within a result set (normalized name+size or infohash) and against `torrents_info()` already present.
- Category ensure-exists, then add via `fileUrl` — skip `descrLink`-only results.
- CLI: `download <tmdb-id>` runs the full pipeline and prints the winner *and its score breakdown* — this is the audit trail until Stage 8.

**Settled:**
- Free space read from qBittorrent's own `server_state.free_space_on_disk` (via `sync/maindata`) — no extra bind mount into the backend, and now actually wired into the pipeline as a pre-add gate (see below).

**Open decisions:**
- [x] Resolution stays a hard 2160p/4K gate — quality tiering applies to source/codec/container *within* it, not across resolutions (no falling back to 1080p). **This was the biggest open call in the plan — reopened and resolved differently mid-Stage-2**, after the user asked whether 1080p fallback would ever be a frontend setting. Landed on: resolution becomes a *floor* setting (`MIN_RESOLUTION`, default `2160p` — so today's default behavior is unchanged) plus the top-weighted pass-two tier, rather than a fixed pass-one token check. See the "Resolution as a floor" deliverable above and `backend/app/score.py`.
- [x] Quality ranking implemented as a weighted composite score, not literal nested tier-group cascading. `resolution_score*10000 + source_score*1000 + codec_score*100 + seeder_score*10 + container_score*1`; known-then-raw seeder count, then size, as final tiebreakers — see `backend/app/score.py`. Reworked three times within Stage 2: first to fold resolution in as the dominant term; then to fold seeder health in as (at the time) the smallest term; then, after a real-world cross-check caught it mattering too little, swapped so seeder health outranks container instead of the reverse — see the decision log for the concrete case that drove that last change.
- [x] Category scheme: one bucket for everything. Single `"movies"` category (`config.CATEGORY`); no movies/TV split (this pipeline is movies-only).
- [x] Exact source/codec/container tier lists and point values — pinned down in `backend/app/config.py`: resolution 2160p/4K(4) > 1080p(3) > 720p(2) > 480p(1); source REMUX(5) > BluRay/BDRip(4) > WEB-DL(3) > WEBRip(2) > HDTV(1); codec HEVC/x265(2) > AVC/x264(1); container MKV(2) > MP4(1); seeder health 100+(3) > 30+(2) > 10+(1), unknown scored the same as tier 1 (viable, not punished — Stage 0's "unknown != zero" — but not rewarded above a verified swarm either). Each tier matches multiple real-world spelling variants (e.g. `WEB-DL`/`WEBDL`, `H.265`/`x265`), found by testing against Stage 0's live sample. `MIN_SEEDERS` (the pass-two viability floor) raised from 1 to 10 in the same pass — a bare "not completely dead" check didn't protect against a genuinely slow download.

**Validation:** Unit tests for the scorer against fixture result sets, including the Dune example above as a named test case, plus messy-field cases (`nbSeeders` of `-1`/`0`, missing `fileSize`, `descrLink`-only). Manual CLI runs against real qBittorrent, including one deliberately hard-to-match title.

**Stage 2 complete.** New modules in `backend/app/`: `qbt.py` (qBittorrent client wrapper — `search()` runs one `search.start()` job to the 55s ceiling with `.delete()` in `finally`, plus `existing_torrent_hashes()`, `free_space_bytes()` via `sync_maindata()`, `ensure_category()`, `add_torrent()`); `score.py` (plugin/result trust filter, pass-one relevance gate — title-variant phrase match, year ±1 tolerance, resolution floor, language allow/blocklist, cam/telesync/screener blocklist — viability gate, dedup by infohash/name+size, pass-two weighted composite scorer with resolution as the dominant tier and seeder health outranking container); `pipeline.py` (`download()` — the fallback loop across Stage 1's variants, gating the ranked winner against qBittorrent's real free space before adding, with a distinct `"insufficient free space"` status alongside `"added"`/`"no qualifying results"`). CLI gained `download <tmdb-id>`, printing the winner and its full score breakdown (now including `resolution_score` and `seeder_score`) as the audit trail. 68 unit tests passing (`backend/tests/`), including the Dune worked example from this file as a named test case, messy-field fixtures (`nbSeeders` unknown/known-zero, missing `fileSize`, jackett-style localhost `fileUrl`), and the resolution-floor/fallback behavior (floor rejects/admits by tier, ranking prefers the higher resolution when both qualify, falls back to the lower one when it's all that's available). One deviation from the plan text beyond the resolution rework: added a `free_space_bytes()` gate that wasn't explicitly listed under Stage 2's deliverables but was already "Settled" as a data source — wiring it in now (skip an over-large winner, try the next-best candidate, else the next variant) matches "fail safe, not best guess" and meant it didn't sit unused until Stage 3.

Manually verified against the real NAS (qBittorrent v5.2.3 at `192.168.0.133:30024`, confirmed reachable and unauthenticated from this network, matching Stage 0): `download 693134` (Dune: Part Two) found 123 qualifying candidates on the first variant and added `Dune Part Two 2024 2160p BluRay REMUX DV HDR ENG LATINO DDP5.1 H265 MP4-BEN THE MEN` (65.8GB, torlock, `nbSeeders` unknown) — resolution 4/source 5/codec 2/container 1. ### Stage 3 — Backend API & persistence
*Depends on: Stage 2, packaged as an importable library.*

**Purpose:** Wrap Stages 1–2 in FastAPI, add the SQLite job store so request state survives restarts, define the API contract the frontend builds against.

**Deliverables / done when:**
- SQLite schema: requests table (id, query text, resolved TMDB id/title, status, timestamps, result-summary fields for the audit trail); a settings table (see Stage 7).
- `POST /api/search` (TMDB candidates), `POST /api/requests` (confirm → enqueue), `GET /api/requests[/…]` (status polling), stub `POST /api/admin/deploy` (real logic in Stage 6).
- `asyncio.Lock`-guarded worker driving one request at a time through: `queued → searching → downloading | no qualifying results | failed → complete`.

**Open decisions:**
- [x] Plain polling (default) over WebSockets/SSE for status updates. Kept the default: `GET /api/requests/{id}` (and `GET /api/requests` for the list view) — no push channel.
- [x] Boot-time recovery sweep — **resolved differently from the plan's literal text.** The plan's draft wording force-failed any row stuck in *either* `searching` or `downloading` on restart. Reopened during this session: `downloading` means a torrent already exists in qBittorrent, independent of this backend — force-failing it on every restart would be a false negative (the download is fine; only this backend's tracking of it was interrupted), violating "hidden, never unrecoverable." Landed on: only `searching` rows (pipeline mid-flight, nothing added yet, that work is genuinely and completely lost) get force-failed to `failed — interrupted, please retry`; `downloading` rows are left untouched and the download watcher just resumes polling them on its next cycle, no special recovery path needed. See `backend/app/db.py`'s `recover_interrupted()`.

**Validation:** API tests with the pipeline mocked, plus one true end-to-end manual run through the API against real qBittorrent + TMDB, including a deliberate backend restart mid-job.

**Stage 3 complete.** New modules in `backend/app/`: `db.py` (`RequestStore` — plain `sqlite3`, no ORM; `requests` table with a JSON `result` blob for the audit trail — variant used, winning candidate, score breakdown, torrent hash; a `settings` table created now as a single seeded-empty-JSON row, schema only, for Stage 7 to define and use); `worker.py` (`Worker` — one `asyncio.Queue`-fed loop processes requests one at a time under an `asyncio.Lock` guarding only the search/score/add phase, driving `queued -> searching -> downloading | no qualifying results | insufficient free space -> failed`; a second, independent loop polls qBittorrent every `DOWNLOAD_POLL_INTERVAL_SECONDS` (10s default) for rows sitting in `downloading` and flips them to `complete` once `progress >= 1` — deliberately *not* holding the pipeline lock, since the actual bittorrent transfer happens inside qBittorrent, outside this backend, and shouldn't block the next queued request); `api.py` (FastAPI app, no CORS — same-origin only, per the confirmed architecture; `POST /api/search` thin-wraps `TMDBClient.search_movie`; `POST /api/requests` resolves the tmdb_id via Stage 1's `resolve()`, persists a `queued` row, and enqueues it; `GET /api/requests` / `GET /api/requests/{id}` for polling; `POST /api/admin/deploy` stubbed at 501, real logic in Stage 6). One deviation beyond the plan's literal deliverables list: **seven** terminal-ish statuses, not Stage 4's originally-stated six (`queued`, `searching`, `downloading`, `complete`, `no qualifying results`, `failed`) — Stage 2 had already added `"insufficient free space"` as a distinct pipeline outcome after that count was written, and it's semantically different from `"no qualifying results"` (found candidates but no room, vs. found nothing), so it's kept as its own status rather than folded into `failed`. Also extended `backend/app/pipeline.py`/`qbt.py`: `DownloadResult` gained `torrent_hash`, captured by diffing `existing_torrent_hashes()` before/after `add_torrent()` (works for both magnet and direct-.torrent-URL winners, unlike parsing `fileUrl` — most real winners are the latter, per Stage 0/2's live sample) — needed so the download watcher knows which torrent to poll; `QBTClient` gained `torrent_info(hash)`. 34 new tests (`test_db.py`, `test_worker.py`, `test_api.py`, plus hash-capture cases added to `test_pipeline.py`), 103 total passing. `requirements.txt` gained `fastapi`, `uvicorn[standard]`, `httpx`; `.gitignore` gained `backend/data/` (the SQLite file's directory).

Manually verified against the real NAS end-to-end through the live API (not just the pipeline), using a disposable test title (Big Buck Bunny, tmdb_id 10378 — a real, legally-torrentable short film with genuine 2160p releases, chosen specifically so this validation doesn't collide with anything the household actually wants, unlike Stage 2's Dune runs) after temporarily lowering `MIN_SIZE_GB` to admit its ~850MB files (reverted immediately after — this exposed and was caught by `test_score.py`'s existing size-floor test, confirming the revert was necessary and complete): (1) `POST /api/requests` → `queued` → `searching`; killed the backend process mid-search and restarted it — the boot recovery sweep correctly marked that request `failed` / `interrupted, please retry`, confirming the resolved open decision above. ### Stage 4 — Touch frontend & same-origin proxy
*Depends on: Stage 3's stable API contract. Single static HTML file.*

**Purpose:** A TMDB-style browsing experience, hand-built: home grid of posters, streaming-provider rows, a detail view, and one button — **Add to Plex** — the only torrenting-adjacent thing the family sees. Also proves the same-origin nginx + backend architecture from a real iPad.

**Deliverables / done when:**
- Home grid from `/api/discover`; tap a provider row to browse its popular titles.
- Detail view with full TMDB info; "Add to Plex" button posts the confirmed request (`POST /api/requests`) — no torrent details ever shown.
- Status list using the six states as distinct visuals, not one spinner.
- One HTML file — markup, CSS, JS together, no build tool, no `node_modules`. TMDB poster images hotlinked directly from TMDB's CDN; every data call goes through the backend proxy.
- Local Docker Compose (nginx + backend) proving reverse-proxy + service-name DNS works from a real iPad on the LAN.
- Web app manifest, apple-touch-icon, standalone display mode. No service worker / offline caching — stale cached job status would be actively misleading.

**Settled:**

### Stage 11 — Post-download file organization & Plex library layout
*Depends on: Stage 10 (needs a real completed episode torrent, plus the show/season/episode identity Stage 9/10 already resolved for it). Closes a real gap the user flagged after Stage 9 shipped: an episode downloaded on its own, under whatever name its release used, doesn't land anywhere Plex's TV agent reliably recognizes as "this show, this season, this episode" — especially across a season's worth of episodes each coming from a differently-named release.*

**Purpose:** Make a completed episode download show up in Plex, in the right show's folder and the right season, without Plex ever having to guess which show a scene-release filename refers to. The key move: this pipeline already knows exactly which show/season/episode a download is for — it resolved that identity *before* searching (Stage 9/10) — so placement is a deterministic write to a known path, not a filename-matching heuristic layered on afterward the way a general-purpose media manager has to do it.

**Deliverables / done when:**
- New `backend/app/media_organizer.py`: `select_video_file(qbt, torrent_hash) -> Path` picks the real episode file out of a completed torrent's file list — the largest file with a known video extension, skipping anything named/sized like a sample. Season packs never reach this code (Stage 10 rejects them in pass one), so "one torrent → one episode's file" is the only case this has to handle — a named, documented gap if a release's structure doesn't fit that assumption, same style as Stage 2's cam-tag gap.
- `organize_episode(show_identity, season, episode, source_path) -> Path`: builds the target path `<TV_LIBRARY_ROOT>/<Show Title> ({year}) {tmdb-<tmdb_id>}/Season <NN>/<Show Title> - s<NN>e<NN>.<ext>` — using Plex's own documented `{tmdb-<id>}` folder-naming hint, so Plex is never left to guess which show a folder belongs to at all. Creates the show/season folders if missing, then **hardlinks** (never moves or renames in place) the source file into that path — the same safe pattern Sonarr/Radarr rely on: qBittorrent's own copy keeps seeding, completely untouched, while Plex sees a second, correctly-named reference to the same bytes at zero extra disk cost. Falls back to a plain copy (logged loudly — it doubles disk usage) only if the target path turns out to be on a different filesystem than the source, where a hardlink can't be created at all.
- `worker.py`'s existing download-watcher calls this exactly once, at the same point a `downloading` row would flip to `complete` — gated on `media_type == 'episode'` only. Nothing changes for movies; qBittorrent alone remains fully responsible for them, exactly as today.
- A new status, `"downloaded, not filed"` — distinct from `complete`, used only when the torrent itself genuinely finished but organizing failed (file-selection ambiguity, missing bind mount, hardlink/copy error). Matches the project's existing pattern of adding a genuinely-distinct status rather than conflating "done" with "needs a human" (the `"insufficient free space"` precedent from Stage 2/3) — an episode a `complete` row claims is watchable actually has to be, per "hidden, never unrecoverable." Surfaced through the existing `/api/admin/jobs`-style raw-JSON visibility (Stage 8) — no new frontend UI, same steer as every other admin-visibility deliverable so far.
- New infra dependency, called out rather than assumed: the backend container needs a **new bind mount** into the same underlying TrueNAS dataset qBittorrent downloads into *and* Plex's TV library already lives on — same filesystem, or the hardlink step above can't work at all. `truenas/custom-app-compose.yaml` gains this mount; the real host path is a build-time NAS detail, not something this planning pass can pin down.
- `config.py` gains `TV_LIBRARY_ROOT` (this container's path to the library root) and a small video-extension/sample-skip constant list — plain module constants for now, matching how Stage 2 introduced its own tuning knobs ahead of any Settings-panel exposure.

**Settled:**
- **Rename/place only after the torrent is fully complete, never mid-download.** The user's own framing ("change the file names once they start downloading") is solved differently on purpose: touching qBittorrent's in-progress file risks its resume data and its own incomplete-file naming, for no benefit — a hardlink placed the moment the download finishes achieves the same practical outcome (Plex sees a correctly-named, correctly-placed file) without ever going near the live download.
- **Identity comes from this app's own resolved metadata, never from re-parsing the downloaded filename.** The show/season/episode a `requests` row already carries (Stage 9/10's resolution, persisted per Stage 12's schema) drives the target path directly — this is what actually closes the "is the correct show detected" concern: Plex is handed an unambiguous `{tmdb-<id>}` folder hint instead of being asked to infer anything from a scene-release name.
- **No new Plex scan trigger.** Stage 8 already declined an automatic scan-on-complete for movies and leaned on Plex's own real-time folder-watching instead; this stage keeps that call for TV too, since the actual bug being fixed is that the file was never somewhere Plex could recognize in the first place — once placement/naming is right, the existing folder-watching this project already depends on should just work.

**Open decisions:**
- [ ] Episode title in the filename (`Show - s01e04 - Episode Title.ext`, needing one more TMDB lookup per organize) vs. `SxxEyy`-only (`Show - s01e04.ext`, both fully valid to Plex) — proposing `SxxEyy`-only as the simpler v1 default; revisit once real episodes are flowing if it turns out to matter for browsing inside Plex itself.
- [x] The real shared-dataset host path on the NAS — **half-settled outside a build session, worth recording rather than re-discovering later:** the user reconfigured qBittorrent's `tv` category save path (previously defaulting to the same folder as `movies`, discovered as a real-world side effect during Stage 10's live validation) to `/media/TV Shows` on the real box — the exact folder Plex's own TV library already points at. So a TV download now lands inside Plex's watched root directly, just not yet organized into the `<Show> ({year}) {tmdb-<id>}/Season NN/` structure this stage builds — that's still real, necessary work, just now happening one level higher in the same folder rather than needing to bridge two different top-level paths. Still open: whether `/media/TV Shows` and qBittorrent's actual download-in-progress path are the same underlying filesystem (needed for the hardlink step, not just the same-looking path) — a `stat`/device-id check against the real box, not guessable from here — and the container-side bind-mount path this stage's compose changes should use.
- [ ] Hardlink-fails-across-filesystems fallback: silently copy (simple, costs disk space) vs. treat it as a hard failure into `"downloaded, not filed"` (matches "fail safe, not best guess" more literally, but might be too strict if the real layout turns out to need it often) — left open pending what the real dataset layout turns out to be.

### Stage 12 — Subscriptions, scheduling & per-episode dedup
*Depends on: Stage 10. ### Stage 13 — Whole-season & complete-series bulk acquisition
*Depends on: Stage 11 (its per-episode file-organizer, extended here to handle many files from one torrent) and Stage 12 (its `show_episodes` dedup ledger, backfilled here so a later per-episode catch-up never re-fetches what a pack already covered). Addresses a real gap the user flagged: a show that's been over for years is exactly the case where per-episode auto-grab (Stage 12) is the wrong tool — hammering an indexer with one search per episode across, say, 8 seasons is slow and often comes back with poorly-seeded (or no) single-episode results, when a well-seeded season or complete-series pack is frequently the only realistic way to get an old show at all.*

**Purpose:** A second, deliberately distinct acquisition mode — "get this whole season" or "get the complete series" in one user-triggered action, as an alternative to (not a replacement for) Stage 12's per-episode standing subscription. Explicitly **not** reopening Stage 10's settled decision that a pack-shaped result is rejected during *episode* search — that gate is unchanged and still protects the per-episode auto-grab loop from ever mis-filing a pack as a single episode. This stage adds its own opposite-shaped gate, used only when the user has explicitly asked for a bulk download, never automatically.

**Deliverables / done when:**
- New pass-one gate (in `score.py` or a small `pack_score.py`) that specifically wants a season-or-more-shaped result: a season token (`s01`, `season 01`) present with **no** accompanying episode token, or an explicit multi-season/complete-series marker (`complete series`, `the complete series`, a season-range token like `s01-s03`). Reuses the existing whole-token utilities unchanged — this is the mirror image of Stage 10's existing "reject a lone season token" rejection, applied deliberately here instead of avoided.
- Query variants built from Stage 9's existing title variants, each tried with a scope suffix: `"{variant} complete series"` for a whole-series request, `"{variant} season {n}"` / `"{variant} S{n:02d} complete"` for a single season — mirrors `tv_resolve.py`'s `episode_query` pattern, just a different suffix shape.
- Scope detection on the candidate set: a v1-simplified classifier that recognizes a single season, or an explicit "complete series" marker, as the only two supported shapes. A partial multi-season range that isn't the full series (`S01-S03` of an 8-season show) is a named, documented gap for v1 — not solved here, same style as Stage 2's cam-tag gap and Stage 9's episode-token-format gap.
- Same pass-two composite scorer as everything else (`score.py`, unmodified) ranks pack candidates exactly like any other release — resolution/source/codec/seeder/container, no pack-specific weighting.
- `media_organizer.py` (Stage 11) gains `organize_pack(show_identity, expected_seasons, torrent_hash)`: enumerates every file in the completed torrent, and for each one that carries its own recognizable `SxxEyy` token, calls the *same* per-file placement logic `organize_episode` already does (season/episode token from the filename itself this time, not from a single fixed request) — so this is an extension of Stage 11's existing function, not a parallel implementation. A file with no recognizable episode token (samples, NFO, subtitle sidecars, an unmatched extra) is skipped and logged, not treated as an error.
- Fan-out on add: one pack torrent add creates **one `requests` row per episode found in it** (all sharing the same `torrent_hash`, `media_type='episode'`) rather than one opaque "pack" row — this is what lets the existing requests list, retention purge, admin/jobs visibility, and per-row `complete`/`"downloaded, not filed"` status all keep working completely unchanged, the same reuse-not-duplicate call Stage 12 already made for scheduled per-episode adds. The one new nuance: the download-watcher's progress poll (keyed on `torrent_hash`) now has to flip a *set* of rows at once instead of one — a straightforward one-to-many update, not new logic.
- Every successfully-organized episode gets a `show_episodes` row inserted (Stage 12's dedup ledger) the moment its file is placed — so a show bulk-downloaded today and subscribed-to tomorrow doesn't have Stage 12's catch-up-on-add logic try to re-search and re-add everything the pack already covered.
- `POST /api/shows/{id}/bulk-download` (body: `{"scope": "series"}` or `{"scope": "season", "season_number": N}`) — a plain, explicit user action, distinct from `POST /api/shows` (subscribe/watch). Usable regardless of the show's own airing status: an ended show is the motivating case, but nothing stops using it to backfill seasons 1-5 of a currently-airing show while staying subscribed for new episodes as they air — both mechanisms can run against the same show at once, since they only ever interact through the shared `show_episodes` ledger.

**Settled:**
- **Bulk acquisition and the standing subscription are independent, not mutually exclusive.** A show can be bulk-downloaded, subscribed-to, both, or neither — `shows`/`show_episodes` don't distinguish how an episode's dedup marker got there.
- **Only two pack shapes supported in v1: one full season, or the complete series.** A show-runner's real-world messy middle ground (an arbitrary season range, a "seasons 1-4" pack for an 8-season show) is out of scope, matching the project's running pattern of naming a known gap rather than half-solving it.
- **No new frontend surface in this stage** — the actual "Download complete series" / "Download season N" controls are Stage 14's job, same split as every other backend-then-frontend stage pairing so far.

**Open decisions:**
- [x] What happens when a pack only partially matches `expected_seasons` — **resolved as "accept what's actually there,"** as leaned toward in planning, but implemented more literally than the plan text anticipated: rather than pre-creating one `requests` row per *expected* episode at add time and reconciling afterward, fan-out happens entirely *after* `organize_pack()` has inspected the pack's real file list — see "Third addendum" below for why, and what that changes about the "fan-out on add" deliverable's literal wording.
- [x] Whether a `pack_score.py` split file is worth it — **yes, built as its own module**, mirroring `tv_score.py`'s own split from `score.py`: the season/series pack gates are a third, clearly-scoped pass-one variant (alongside movies' and episodes'), and keeping them out of `score.py` keeps that file about movie-and-TV-shared release-quality logic only, not also "how to detect three different result shapes."

**Validation:** Unit tests mirroring Stage 10's — fixture pack results (a real-shaped complete-series listing, a single-season pack, and a plain season-pack-with-no-episode-token that must still be *accepted* here even though Stage 10 rejects the identical shape in its own context, proving the two gates are genuinely independent) — plus a multi-file organize test (a fixture torrent with several `SxxEyy`-tagged files and one unmatched extra) confirming every real episode gets its own row, its own placed file, and its own `show_episodes` entry, and the extra is skipped without error. Deliberately no new `scope` column: `season_number` set means "season N," left `NULL` means "complete series" — the two are already fully distinguishable this way, and `episode_number` stays `NULL` on a pack row always, since a pack is never about one specific episode.

**A real, flagged deviation from the plan text's literal "fan-out on add" wording**, not a silent reinterpretation: the plan's deliverables list describes creating one `requests` row per episode immediately once the pack torrent is added, sized off TMDB's own expected episode count for the target season/series. Building it that way would mean either guessing at exactly which episodes a pack contains before a single byte of it has downloaded, or building a second reconciliation pass to fix up wrong guesses once the real file list is known — and it would directly conflict with the "accept what's actually there" resolution of this stage's own open decision, since a row created from an *expected* count has no honest way to represent "this pack turned out to be missing episode 7." Fan-out instead happens once `worker.py`'s `_check_downloading` notices the pack's torrent has reached 100% and calls the new `_organize_and_complete_pack()`: it runs `organize_pack()` first, and only for each `(season, episode)` tuple it actually returns does a normal episode `requests` row get created (via the same `create_episode_request` Stage 12 already built), immediately marked `complete` with a `result.note` explaining it came from a bulk download, and given a `show_episodes` ledger marker — skipping any `(season, episode)` `has_show_episode` already covers, so a pack overlapping something the per-episode scheduler (or an earlier pack) already handled doesn't create a duplicate audit-trail row for the same file. The pack's own tracking row earns `complete` only once this fan-out finishes; a `MediaOrganizerError` (torrent gone, or literally nothing recognizable inside it) lands it on `"downloaded, not filed"` instead — the exact same vocabulary a single-episode organize failure already uses. The practical effect for the requests list: while a bulk download is in flight it shows as one `pack` row, and once it completes that row is joined by one `episode` row per episode the pack actually turned out to contain — fully satisfying this stage's own "the requests list shows them individually" validation goal, just at completion time rather than at add time.

`worker.py`'s `_run_one` gained a third `media_type` branch (`'pack'` → resolve the show, then call `download_pack` with `scope` inferred from whether `season_number` is set) reusing the exact same result-handling/logging path movie and episode rows already go through — `_result_summary`'s output gained an optional `query_used` key (via `getattr(result, "query_used", None)`) rather than forking a pack-specific summary builder, since that's the only field `PackDownloadResult` carries that the other two result types don't. `_check_downloading`'s "torrent disappeared" branch now treats `'pack'` the same way it already treats `'episode'` (skip the Plex check — no TV-shaped lookup exists — and report an unconfirmed removal), and its progress-reaches-1.0 branch gained the `'pack'` case calling `_organize_and_complete_pack`.

`api.py` gained `POST /api/shows/{show_id}/bulk-download` (body: `{"scope": "season", "season_number": N}` or `{"scope": "series"}`, validated by a new `BulkDownloadRequest` Pydantic model whose `model_validator` enforces the two are used correctly together) — creates a `pack` request row and enqueues it into the same worker queue every other download goes through, so a bulk download never races a queued movie/episode search. Deliberately independent of a show's `watching`/`paused` status (no check against it at all), matching the plan's "usable regardless" call — verified with a dedicated test subscribing, pausing, then bulk-downloading successfully anyway. `cli.py` gained `bulk-download <tmdb-id> <season|series> [--season N]` and `organize-pack <tmdb-id> <torrent-hash>`, mirroring `download-episode`/`organize-episode`'s manual dev-entry-point pattern — not because this stage needed a CLI-first phase the way Stage 10/11 did (the API/worker wiring was built directly, same as Stage 12's own precedent of skipping a CLI stand-in once real wiring exists), but as a lower-friction way to drive `download_pack`/`organize_pack` directly against real TMDB/qBittorrent for manual validation, same as every prior stage's CLI commands have doubled as.
